# Risks and technical debt

Sources: the deployment audit [`docs/deployment_audit/speaker.md`](../deployment_audit/speaker.md) (2026-11-04, `[C]` = checked in the code) and a reading of the code for this document (2026-11-05). Nothing here was fixed by the documentation work.

| ID | Item | Impact | Mitigation / next step |
|---|---|---|---|
| R-1 | **Fixed 2026-11-10 (ADR-012, T-01.2, T-01.3):** `SPEAKER_BACKEND=null` starts with no device and no PortAudio; with `real` and no device the process still does not start, on purpose. Run as the real service, through the pipeline check and in Docker on amd64 on 2026-11-10 (T-03). Original: **No device, no process.** `SoundDeviceAudioPlayback.__init__` calls `selector.select()` and raises `SpeakerUnavailable` while `new_http_container` builds the app, before uvicorn runs. There is no null sink (0 matches in the production code). `/available` therefore never answers false and Brain's pre-flight just cannot reach the service | A machine without a sound card (a server, a CI run, a Docker host) cannot run the service at all | FR-15: a `null` backend behind `AudioPlaybackPort` (proposed) |
| R-2 | **Fixed 2026-11-10 (T-01.2):** the driver is imported only on the `real` branch; a test makes `sounddevice` unimportable and `null` still starts. Original: `sounddevice` is imported at module level (`sounddevice_driver.py`, reached from `audio_playback_dependency.py`) | Without PortAudio the import itself fails, so even a null backend chosen later crashes on a machine without PortAudio | FR-15: choose the backend in the composition root **before** importing the driver (lazy import) |
| R-3 | **Device keywords matter on Linux, not on Windows.** On the Windows PC checked no output device name contains a default keyword, so the OS default is used and works. On Linux `hw` or `default` can match the first ALSA device (for example HDMI) before the wanted one | The wrong device plays | Set `SPEAKER_DEVICE_INDEX`; FR-17: keywords per machine in the deploy config |
| R-4 | **Closed 2026-11-10 (T-01.4):** on `null` `/available` carries a note in its `reason` (no `contracts` field, decided 2026-11-09), and the service logs a warning at start. Original: `/available` cannot say which backend is active: `AvailabilityResponse` has only `is_available` and `reason` | A null sink and a real one look the same to Brain | FR-16: a `backend` field in `contracts` (new version, then producers and consumers) |
| R-5 | **Fixed 2026-11-10 (T-01.5, T-02.1):** dev tools moved to `requirements.dev.txt` (named `requirements-dev.txt` until 2026-11-11), `numpy`, `soundfile`, `websockets` and `libsndfile1` dropped, the four runtime packages pinned (transitive packages not locked). Original: Runtime requirements list dev tools (pytest, ruff, black, mypy), packages the code does not import (`numpy`, `soundfile`, `websockets`; `httpx` is used only by tests), all unpinned; the catalogue `apt` list has `libsndfile1` for nothing | Slower and less reproducible installs | Split dev requirements, drop the unused ones, pin ranges (not done: not asked) |
| R-6 | ~~The end of a playback is bounded to 3 seconds.~~ **Fixed 2026-11-09.** The service used to wait at most 3 s (`_DRAIN_TIMEOUT_SECONDS`) after the body ended for the queue to be written and then drop the rest (`Playback queue cleanup timed out; truncating`). tts synthesizes faster than real time and Brain does not pace the stream, so the whole reply is queued at once and any reply longer than about 3 s was cut: confirmed on a real device on 2026-11-09 (tts T-01.1.6), a 7.15 s sentence played for about 3.0 s (`written_bytes=145408` of `queued_bytes=343068`) while the call still answered `success: true`. **Now** the wait is the duration of the audio that was queued plus 2 s (`_drain_timeout_seconds`, `_DRAIN_MARGIN_SECONDS`): an upper bound of what is left, because the device has been playing it since the start, so a reply that plays normally is never cut and a stalled device still ends the session; tested with a real-time fake device (a 3.5 s reply is written in full; 9 of 9 one-line mutations caught). **Seen on a real device after the fix (2026-11-09, output device 3, 24 kHz mono, tts and the fixed speaker from scratch copies, each reply handed to the speaker in one request like Brain's stream): the 7.12 s sentence was written in full (`written_bytes` 341,578 of `queued_bytes` 341,578), the speaker answered after 7.27 s (it played for its whole duration), and the 3.05 s and 0.74 s sentences were also written in full; no truncation warning. The client was a small script, not Brain; the maintainer listened and confirmed that all three sentences were heard in full.** A playback that does hit the bound is still only logged (a warning with `queued_bytes` and `written_bytes`) and answered `success: true`. **Since 2026-11-10 (T-01.6) it answers `success: false` (`Playback did not finish: the device played X of Y bytes before the wait ran out`) and the handler sends a `playback_failed` event; Brain was read first: the speaker's stream is answered when the request body ends, so a failure reaches Brain at the end of the pipeline as an `ExternalServiceUnavailableError`, the same path as any playback failure** | Speech cut at the end (fixed); a truncation by a stalled device is now reported (fixed) | Done |
| R-7 | The reader's queue is unbounded and the body has no size or duration limit | A fast or endless sender grows memory and holds the device | Bound the queue (back pressure on the request stream) if a caller other than Brain appears |
| R-8 | No authentication, and a new request supersedes the running one (ADR-004, ADR-008) | Whoever reaches port 8003 can play audio and interrupt Brain's speech | Network limits now; the common auth middleware later |
| R-9 | CORS `*` by default | Any browser origin may call the service | List the origins where a browser reaches it |
| R-10 | **Retested 2026-11-10 (T-01.7), partly:** `tests/simple.py`, other sample rates, the probes, supersession and the release of the device passed on the real device (index 3) with the maintainer listening; this also found and fixed the replaced-while-draining defect (R-17). Not exercised: the resampler (the device accepted every rate), Linux and Docker with `/dev/snd`. Original: **Hardware not retested.** The 84 tests use a fake driver; real playback (`tests/simple.py`, the adapter on a real device), device-rate resampling on hardware and Docker with `/dev/snd` have not been run in the last passes | The status is "working, needs retest", not "verified" | Run `tests/simple.py` on a machine with an output device |
| R-11 | **Decided 2026-11-09 (Q01-4, ADR-011 update), built in the deploy tool 2026-11-10 (T-02.3):** the rejection stays for `real`, a speaker on `null` may run in Docker on Windows (`simulated_when`); no per-machine `mode` key. Original: Windows Docker: not reachable; the deploy tool rejects a Docker speaker on Windows and has no per-machine `mode` key (decision of 2026-11-04, ADR-011, not implemented) | A layout with a Docker speaker on Windows is refused | Implement the local override in the deploy tool |
| R-12 | Lint: `ruff` (microphone venv) reports 8 findings here, 4 auto-fixable; `ruff`, `mypy` and `black` are not installed in this venv | Style debt | Not fixed on purpose: do not bulk-fix lint unasked |
| R-13 | Stale material: `docs/old/` (previous layout, removed auth, removed autoloader), `.engram/` (old notes, some wrong), the legacy README and AGENTS files | A reader may take removed features for current ones | They are archives; the current documents are the ones linked from the README. Do not reintroduce the autoloader or the auth |
| R-14 | `SpeakerService.is_available()` and the port method of the same name return "a playback is running" but no route uses them: `/available` calls `check_readiness` | A name that suggests something the endpoint does not mean | Remove it or rename it when the port is next changed |
| R-15 | `docs/deployment_audit/` is not committed (untracked) | The audit may be lost | The maintainer decides whether to commit it |
| R-16 | **Fixed 2026-11-10 (`timeout_graceful_shutdown` = 5 s): with a 20 s playback in flight `docker stop` now takes 5.73 s and exits with code 0 and the cleanup logged.** Original: **`docker stop` waits for a playback in flight.** uvicorn's graceful shutdown waits for the open request, so a stop with a long playback runs until the playback ends: 18.55 s for a 20 s playback with a 30 s grace period (exit code 0, the device is released and the cleanup logged), or, with Docker's default 10 s grace period, 10.49 s and a kill (exit code 137, no cleanup log, the sender gets an incomplete read). One earlier run ended in 1.64 s with exit code 137 and was not explained. Found by the Docker run of 2026-11-10 (T-03.3); the microphone has the same with a connected `/stream` consumer | A stopped or recreated container interrupts speech after up to 10 s and skips its own cleanup; the OS releases the device when the process dies | Fixed with uvicorn's `timeout_graceful_shutdown` (close the connections after a few seconds so the lifespan cleanup runs), or cancelling the running playback on SIGTERM before uvicorn waits |
| R-17 | **Fixed 2026-11-10 (found by the real-device retest T-01.7).** A playback replaced while it was still draining held its request for the whole drain bound and then answered `success: false` (after T-01.6; success before it), and its end reset the shared state of the newer playback | A replaced reply looked like a failed playback to Brain and could cut the newer reply short | `_wait_for_drain` ends as soon as the session is replaced and the old session leaves the shared state alone; two tests, 8 of 8 mutations caught, confirmed on the real device |
