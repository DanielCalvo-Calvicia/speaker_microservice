## Addendum (2026-11-10): found on the real device (T-01.7)

The `success: false` answer exposed an older flaw when the real device played a replaced playback: a playback that was **replaced while it was still draining** (its whole body already queued, the device part-way through it, then a newer request) did not end at once: its drain wait could never finish because the newer request had cancelled its worker, so it held the caller's request for the whole bound (8.24 s for 6 s of audio) and, with the T-01.6 change, answered `success: false` (`Playback did not finish: the device played 0 of 288000 bytes ...`), which Brain would have taken for a failed playback; before T-01.6 it answered success after the same delay. A second flaw sat next to it: when that wait ended, the old session reset `_is_playing` and `_current_session`, which belong to the newer one, so it could have cut the newer playback short. `_wait_for_drain` now ends with `replaced` as soon as the session is no longer the current one (looked at every 0.1 s), the session answers "Playback session superseded by new request" (success) and leaves the shared state alone. Tests written first (the first failed on the old code with `success: False`): `test_a_playback_replaced_while_it_drains_ends_at_once_as_superseded_not_as_a_failure` and `test_the_end_of_a_replaced_playback_does_not_cut_the_newer_one_short`; 8 of 8 one-line mutations of the new code caught; 120 tests, ruff 7 findings and mypy 4 errors as before. See the Result of T-01.7.
