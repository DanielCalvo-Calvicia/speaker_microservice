## Goal

A machine or a tool that reads `GET /available` can tell a null sink from a real device (R-4), and the log says it once at start. **Written for option (a) of Q01-2** (the `reason`, no `contracts` change); if the maintainer chose (b), this task changes: contracts goes first with a version bump and every service re-bundles (stop and re-plan).

## Specification

- `/available` on `null`: `is_available: true`, `reason` = the note; on `real` with a device: `is_available: true`, `reason: null` (unchanged); on `real` without a device the process does not start (unchanged: F6).
- `is_available` never turns false because of the null backend (Brain's preflight would exit).
- `GET /health` is unchanged.

## Acceptance criteria

The handler test shows the note on `null` and no note on `real`; the deploy tool's `healthy and available, warning: <reason>` line is exercised in T-02.2 and T-03.2.

## Verification

Tests and mutations (note dropped, `is_available` flipped, note shown on `real`) all caught.

## Result (2026-11-10)

Done with the answer of Q01-2 (the `reason`, no `contracts` change): `/available` on `null` answers `is_available: true` and `reason` = "null sink (SPEAKER_BACKEND=null): audio is discarded, nothing is played" (tested through the container), on `real` with a device `reason: null` (unchanged), and the service logs one warning at start. `handle_ready` passed the same message as `pending_reason`, so a null note would have shown as something pending on a ready service: it is now sent only when `is_ready` is false (test with a not-ready, a ready-with-a-note and a plain service; mutations: 3 of 3 caught). `/health` is unchanged. `GET /available` is what the deployment tool and Brain's preflight read; Brain ignores the reason when available, as ADR-012 says.
